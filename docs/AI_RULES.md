# AI Development Rules

## Purpose

This document defines the rules that AI coding assistants must follow when working on Smart Expense Tracker.

These rules apply to Codex, ChatGPT, Claude Code, GitHub Copilot, and other AI development tools.

## Project Scope

Before making changes, review:

- `README.md`
- `docs/ARCHITECTURE.md`
- `docs/ROADMAP.md`
- `docs/DECISIONS.md`

Do not implement features that are outside the current development milestone.

Prefer small, testable, and documented changes over large rewrites.

## Architecture Rules

- Keep responsibilities separated between modules.
- Keep `main.py` focused on CLI interaction and orchestration.
- Do not place business logic inside input or output code.
- Keep validation separate from the `Transaction` model.
- Keep storage logic separate from the CLI.
- Keep reporting logic separate from output formatting.
- Avoid global mutable state.
- Reuse existing functions instead of duplicating logic.
- Do not create unnecessary abstractions or overengineer the project.

Future input methods such as CLI, Excel, Telegram Bot, GUI, and API must reuse the same validation, transaction creation, ID generation, application services, and repository logic.

## Transaction Rules

Each transaction has:

- An internal UUID
- A user-facing display ID such as `T-0001`

Both identifiers must remain unchanged during normal updates.

Display IDs must be:

- Unique
- Consistent
- Searchable
- Generated by centralized logic
- Never reused after deletion

Do not introduce financial calculations using `float`. Monetary values use
`Decimal` and current persistence schemas store canonical decimal text.

## Data Protection

- Do not modify real user data during testing.
- Use temporary files or databases for tests.
- Do not break the current JSON format without a migration plan.
- Do not delete or overwrite transaction data without explicit approval.
- Do not commit passwords, tokens, API keys, database files, or private financial data.
- Do not store Telegram Bot tokens or other secrets directly in source code.

## Documentation Rules

All project documentation must be stored inside:

```text
docs/
```

The only Markdown file allowed in the project root is:

```text
README.md
```

When a change affects architecture, roadmap, testing, releases, or technical decisions, update the related documentation.

Important technical and architectural decisions must be recorded in:

```text
docs/DECISIONS.md
```

Do not create unnecessary Markdown files.

## Testing Rules

For every confirmed bug:

1. Reproduce the bug.
2. Add a failing regression test.
3. Fix the bug.
4. Run the relevant tests.
5. Run the complete test suite when practical.

Do not remove or weaken valid tests only to make them pass.

Never claim that tests passed unless they were actually run.

Tests must not modify real user data.

## Coding Standards

Use:

- Clear names
- Type hints
- Small focused functions
- Explicit return types
- Meaningful exceptions
- Minimal duplicated logic
- Standard Python naming conventions

Avoid:

- Hard-coded paths
- Hard-coded secrets
- Silent failures
- Broad exception handling without justification
- Unnecessary dependencies
- Unrelated refactoring
- Premature abstraction

Do not add a third-party dependency unless it solves a current requirement and is properly documented.

## Git Rules

Before changing code:

- Check the current branch.
- Review relevant code and documentation.
- Confirm the requested scope.

After meaningful work:

- Review `git diff`.
- Run relevant tests.
- Update documentation.
- Prepare one focused commit.

Commit messages must be concise, imperative, and written in English.

Examples:

```text
Fix initial transaction display ID
Add tests for transaction search
Document version 2 architecture
```

Do not:

- Force-push
- Rewrite Git history
- Delete branches
- Commit secrets
- Combine unrelated changes in one commit
- Push changes without explicit approval

## Completion Rules

A task is complete when applicable items are done:

- The smallest working change is implemented.
- Relevant tests pass.
- Existing behavior remains stable.
- Documentation is updated.
- Changed files are reviewed.
- A meaningful commit message is prepared.
- The next exact step is identified.

At the end of each work session, report:

- Completed work
- Changed files
- Recommended commit message
- Exact next step
